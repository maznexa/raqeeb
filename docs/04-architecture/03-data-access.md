# Data Access — Drizzle, Transactions, Ordering, JSONB Cache

> **Status:** Accepted.
> ORM: **Drizzle**. Schema lives in `packages/db` and is the implementation source of
> truth for the entire data model (the docs in `docs/03-domain-model/` are descriptive).

## Drizzle conventions

### ADR: Drizzle over Prisma/TypeORM/raw SQL

**Decision.** Drizzle ORM with **hand-edited SQL migrations**.

**Rationale.**
- Migrations are plain SQL files we own: RLS policies, `FORCE ROW LEVEL SECURITY`, GIN
  indexes, triggers, and partitioning ride in the *same* migration as the table they
  protect — no second "raw SQL escape hatch" pipeline where security DDL gets forgotten.
- Explicit connection control: `withTenant()` needs `BEGIN; SET LOCAL ...` on a specific
  pooled client; Drizzle hands us the client, Prisma's engine hides it.
- Composable `sql` fragments for the heavy lifting this product needs (recursive CTEs for
  folder trees and dependency DAG walks, profitability aggregations later).
- No engine binary/sidecar; plain TypeScript in every runtime (API, worker, scripts).

**Rejected alternatives.**
- *Prisma*: engine binary, weak `SET LOCAL`/per-transaction-client ergonomics, migrations
  generated in a DSL that fights hand-written RLS/partition DDL.
- *TypeORM*: decorator entity drift, weak typing on raw queries, migration story worse
  than plain SQL.
- *Raw SQL only*: loses inferred types shared to `packages/contracts` and the web app.

### Rules

1. **Schema source of truth:** `packages/db/src/schema/*.ts`. Table files mirror the
   domain modules. Every tenant table exports its `tenant_id` column via a shared helper
   so the "has tenant_id ⇒ has RLS" CI canary can introspect.
2. **Migrations:** generated by `drizzle-kit` as a starting point, then **hand-edited** —
   the committed artifact is SQL. Each migration that creates a tenant table MUST include
   in the same file: `ENABLE`/`FORCE ROW LEVEL SECURITY`, the tenant policy (scalar-
   subselect pattern), grants to `raqeeb_app`, and the composite indexes leading with
   `tenant_id`. Reviewers reject migrations that split these.
3. **Drift check in CI:** `drizzle-kit check` (schema ↔ migrations) runs in CI; a diff
   fails the build. Nobody edits the database that isn't a migration.
4. **No raw pool access outside `packages/db`:** ESLint boundary rule. Application code
   receives a transaction handle from `withTenant()` / `withSystem()`.
5. **Naming:** snake_case in SQL, camelCase in TypeScript (Drizzle mapping); FK columns
   `{entity}_id`; partial indexes named `{table}_{cols}_{predicate}_idx`.

## Transaction helper

```ts
// packages/db/src/tenant.ts (shape, not verbatim)
export async function withTenant<T>(
  tenantId: string,
  fn: (tx: Tx) => Promise<T>,
): Promise<T> {
  const ambient = txStorage.getStore();
  if (ambient) {
    if (ambient.tenantId !== tenantId) throw new TenantContextMismatch();
    return fn(ambient.tx);                       // join ambient transaction
  }
  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    await client.query("SELECT set_config('app.current_tenant_id', $1, true)", [tenantId]);
    const tx = drizzle(client);
    const result = await txStorage.run({ tenantId, tx }, () => fn(tx));
    await client.query('COMMIT');
    return result;
  } catch (e) {
    await client.query('ROLLBACK');
    throw e;
  } finally {
    client.release();
  }
}
```

Properties: GUC is transaction-local (`set_config(..., true)`), parameterized (never
string-interpolated), context propagated via AsyncLocalStorage so services deep in the
call stack join the same transaction; commit/rollback owns the event-outbox atomicity
guarantee (`04-realtime.md`). `withSystem()` is the same shape with `app.is_system` and
lives behind a separate import path that lint flags outside the allowed modules.

## Fractional ordering (D10) — implementation spec

**Keys.** Generated with the `fractional-indexing` algorithm (base-62 digit strings,
lexicographic order, a key can always be generated between any two keys). Stored as
`position text NOT NULL`, collation `C` (byte order — locale collations would corrupt
ordering). Applies to task_locations, sections, projects, folders, spaces, statuses.

**API contract.** Clients never see or send keys:

```
POST /api/v1/tasks/{id}/locations/{locationId}/move
{ "insert_after": "<taskId>" }          // or "insert_before", or "section_id" + first/last
```

The server loads the two neighbor keys inside the mutation transaction and computes the
new key. Response returns the ordered neighbors, not the key.

**Collision handling.** Two concurrent inserts into the same gap can compute the same key.
`UNIQUE(tenant_id, project_id, section_id, position)` is intentionally **not** declared
(ties are legal transiently; ordering ties break by `id`), but the generator adds jitter:
when generating between a and b, it randomizes the appended digit so concurrent writers
diverge. If a write still lands equal to a neighbor (detected on read-back), the mutation
retries with fresh neighbors — bounded retry (3×) with jitter, then surfaces 409.

**Rebalance job.** Keys grow one character per repeated same-gap insertion. A low-priority
`rebalance` queue job (see `05-jobs.md`) scans for lists whose max key length exceeds a
threshold (64 chars) and rewrites the list's keys to short evenly-spaced values in batched
transactions (500 rows/batch, ordered, idempotent — safe to re-run). Rebalancing changes
keys only, never relative order; since clients never hold keys, nothing invalidates.

**Never NUMERIC.** `NUMERIC(12,6)` midpoint schemes exhaust precision after ~20 adjacent
inserts and force synchronous renumbering — rejected in D10.

## JSONB custom-field cache rules (D4, ships P2)

The typed `custom_field_values` table is the **source of truth**; `tasks.custom_fields_cache
jsonb` (shape: `{ "<field_id>": <normalized value> }`, GIN `jsonb_path_ops`) exists purely
to make task-list rendering and filtering one-table cheap. Rules:

1. **Containment filters only.** The cache serves `@>` containment queries
   (`custom_fields_cache @> '{"<field_id>": "opt_a"}'`) — i.e. equality/has-value filters
   on select, checkbox, people, text-exact. That is what `jsonb_path_ops` GIN accelerates.
2. **Sort and range go to the typed table.** ORDER BY a number/date field, `between`,
   `>`/`<` filters, and aggregation always join `custom_field_values` on its typed,
   B-tree-indexed columns. The query planner in `TasksService.listQuery()` picks the path
   by operator — never "try JSONB first".
3. **Same-transaction writes.** Any write to `custom_field_values` updates the task's
   cache **in the same transaction** (single `jsonb_set`/rebuild statement). There is no
   async cache fill; a torn write is impossible by construction.
4. **Nightly consistency check.** A scheduled job (reconciliation queue) rebuilds the
   cache expression for a sample (all tenants, rotating window) and compares against the
   stored cache; mismatches are metric-counted, logged with tenant/task ids, and repaired.
   Rising mismatch count = code bug alarm, not data cleanup routine.
5. **Cache is disposable.** A `rebuild-field-cache` maintenance command regenerates it
   from the typed table for a tenant/project; nothing reads the cache as truth.

## Query discipline for the perf budgets

- Task lists resolve through `task_locations (tenant_id, project_id, section_id, position)`
  — index-ordered, keyset-paginated (cursor = position + id), no OFFSET.
- Folder trees and dependency walks use recursive CTEs with depth guards (5 for folders;
  dependency cycle check bounded by graph size with a hard cap).
- N+1 is prevented at the contract layer: list endpoints return exactly the documented
  sparse fieldset; expansions are explicit `fields=` opt-ins (see API conventions).
- `EXPLAIN (ANALYZE, BUFFERS)` snapshots for the hot queries are committed under
  `packages/db/bench/` and re-checked by the nightly 50k-task fixture run
  (`08-observability-performance.md`).
